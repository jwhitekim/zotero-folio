# 기술 스택 선택 근거와 확장 로드맵

현재 Node.js(Express) + Svelte 스택 채택 이유, 향후 대규모 사용자 대응 시 필요한
변경 사항 정리. 2026-09-17 논의 기록.

## 1. 현재 스택 선택 근거

### 서버: Node.js(Express), Python(Django) 아님

Folio 서버가 하는 일은 대부분 Zotero API 호출 대기, 응답 프록시, 마크다운
변환처럼 짧고 가벼운 처리다. 복잡한 데이터 모델, 관리자 화면, 다수 개발자
협업 같은 Django가 강점을 보이는 조건에 해당 사항 없음.

I/O 대기 중심 작업(네트워크 요청 응답 기다리기)은 Node의 비동기 이벤트
루프 모델과 궁합이 좋음.

```js
const res = await fetch(zoteroApiUrl); // 대기 중 다른 요청도 동시 처리
```

추가 근거: 프론트(Svelte)도 JS라서 서버까지 JS로 통일하면 언어 1개 + 빌드
시스템 1개 + 서버 하나로 통합 배포 가능. Python으로 서버를 분리하면 언어
경계가 하나 늘어 배포·공유 코드 관리 부담만 증가.

### 프론트: Svelte, React 아님

`.svelte` 파일은 마크업(HTML)·로직(JS)·스타일(CSS)을 한 파일에 담는 컴파일러형
프레임워크 — Vue의 `.vue`, React의 `.jsx`와 같은 역할. Folio 프론트 규모(탭
4개 수준)에서는 React 같은 런타임 가상 DOM(Document Object Model) 프레임워크의 생태계 이점(상태
관리 라이브러리 다양성, 대규모 팀 협업 관습)이 크게 필요하지 않음. Svelte는
빌드 시점에 컴파일해 런타임 오버헤드가 작고 번들 크기가 가벼움 — 개인용
도구 성격과 부합.

## 2. 비동기(async/await)의 실제 한계

JS는 "동기 언어"가 아니라 싱글 스레드 + 이벤트 루프 모델. `await`로 처리하는
I/O 대기(네트워크 요청)는 여러 사용자 요청이 동시에 진행되는 것처럼 동작하지만,
**CPU 연산(마크다운을 HTML로 변환하는 작업 등)은 여전히 한 줄씩 순차
실행** — 연산이 끝날 때까지 프로세스 전체가 멈춤.

```js
const html = marked.parse(longMarkdownText); // 순수 계산, await 불가
```

zotero-insight 서버(`server/`) 코드 125곳이 `async`/`await` 패턴 — I/O
구간은 이미 비동기로 구현됨. 남은 리스크는 CPU 연산 구간이 겹치는 극단적
동시 접속 상황뿐.

## 3. 현재 구조의 확장 한계

| 항목 | 현재 상태 | 한계 |
| --- | --- | --- |
| 세션 저장소 | `express-session` 기본 MemoryStore | 프로세스 메모리에 세션 누적, Express 공식 문서도 운영 환경 비권장, 서버 재시작 시 전체 세션 소멸 |
| 프로세스 구성 | Node 단일 프로세스, Docker 컨테이너 1개 | 코어 1개만 사용 — 서버 스펙(코어 수)을 올려도 코드 구조상 나머지 코어 활용 불가 |
| DB | Supabase(Postgres), 이미 전환 완료 | 동시 쓰기 처리량은 병목 아님(SQLite 대비 개선됨) |
| Zotero API 요청 한도 | 사용자별 개인 OAuth 토큰 사용 | 사용자 간 영향 없음, 병목 아님 |

## 4. 실서비스 전환 시 변경 항목

소규모(개인·지인 단위) 운용에서는 불필요, 대규모(수백~수천 동시 접속) 전환
시에만 필요.

### 4-1. 세션 저장소 교체: MemoryStore(현재 상태)에서 Redis로

`express-session`의 저장소(store) 옵션을 Redis 기반으로 교체. 여러 프로세스가
같은 세션을 공유해야 하는 4-2와 맞물려 있어 함께 적용 필요.

### 4-2. 멀티프로세스화 — PM2 또는 Node `cluster` 모듈

서버 스펙(CPU 코어 수)을 올리는 것과 반드시 함께 적용. 코드 구조 변경 없이
하드웨어만 업그레이드하면 Node가 코어 1개만 쓰므로 효과 없음. PM2로 코어
개수만큼 프로세스를 띄우고 로드밸런싱하면, 한 요청의 CPU 연산이 다른 요청
전체를 막는 문제가 프로세스 단위로 분산됨.

### 4-3. 관련 없는 변경 — 프론트엔드 프레임워크 교체

Svelte를 React 등으로 바꾸는 것은 서버 성능·동시 접속 처리와 무관. 브라우저
렌더링 계층 문제이지 서버 이벤트 루프 문제가 아니므로 확장 대응 항목에서
제외.

## 5. 우선순위 요약

1. 세션 저장소(Redis)와 멀티프로세스화(PM2)는 세트로 적용 — 둘 중 하나만
   해서는 효과가 제한적.
2. DB(Supabase)는 이미 대응 완료 상태.
3. 프론트엔드 프레임워크 교체는 위 확장 로드맵과 무관, 별도 판단 필요.

현재는 위 항목 전부 미착수 상태 — 소규모 운용 범위에서는 지금 구조 유지가
합리적 선택.
