# 앱 배포 가능성 — 탐색 메모

배포 계획이 확정된 상태 아님. 윈도우 데스크톱 앱화 가능성을 가볍게
논의한 기록.

## 현재 아키텍처 전제

Express 서버 + Svelte 프론트엔드 정적 서빙 구조. 데이터는 Supabase
(클라우드), 로그인은 Zotero OAuth(클라우드) — 이미 "로컬 전용 앱"이
아니라 "브라우저로 접속하는 웹 서비스"에 가까운 형태. 데스크톱 앱으로
포장해도 인터넷 연결 없이는 동작 불가.

## 패키징 방식 비교

| 방식 | 특징 |
| --- | --- |
| Electron | 구현 난이도 가장 낮음(서버 코드 무변경). Chromium 번들로 용량 큼(통상 100MB 이상). 웹앱을 창으로 포장하는 수준 |
| Tauri | 시스템 웹뷰 사용으로 용량 훨씬 작음(수십MB 이하). 러스트 툴체인 필요 — 진입 장벽 존재 |
| 로컬 실행 파일 + 브라우저 | `pkg`/`nexe` 등으로 서버를 실행 파일화, 더블클릭 시 로컬 서버 기동 후 브라우저 자동 오픈. 작업량 가장 적지만 "앱" 느낌은 약함 |

## 서버 리소스 관점(i5 8세대, RAM 16GB, Windows 기준)

Node 프로세스 자체 소비량은 유휴 시 수십MB 수준, PDF/HTML 첨부파일
다운로드 시(현재 전체 버퍼링 방식, [repo-proof/audits/](../repo-proof/audits/)
findings.md의 4번째 항목 참고) 논문 크기만큼 일시 스파이크 — 해당
사양에서 병목 요인 아님.

체감 여유가 적은 원인은 앱이 아니라 운영체제 오버헤드 쪽으로 확인.
윈도우는 유휴 상태에서도 백그라운드 서비스·GUI 셸이 기본으로 상당량
점유(통상 1.5~3GB대), 헤드리스 리눅스 서버 배포판 대비 큼. Docker
Desktop for Windows를 쓰는 경우 WSL2(Windows Subsystem for Linux 2)
가상머신 오버헤드가 추가로 붙어
체감 점유율을 더 키움.

## 배포를 실제로 고려할 경우 먼저 확인할 것

- Supabase를 계속 클라우드에 둘지, 셀프호스팅할지(셀프호스팅도 해당
  사양 1인/소규모 기준으로는 충분히 감당 가능)
- 배포가 "1인이 여러 기기에서 접근"인지 "여러 사용자에게 서비스 제공"
  인지 — 후자는 [scope-discipline-notes.md](scope-discipline-notes.md)의
  범위 확인 절차 적용 대상
- 데스크톱 앱화 목적이 "오프라인 사용"이면 현재 아키텍처(Zotero
  OAuth·Supabase 의존)와 상충 — 목적 재정의 필요
