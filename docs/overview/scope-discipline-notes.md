# 범위 관리 원칙 — 규모 확대 시 놓치기 쉬운 지점

RepoProof 외부 감사(`repo-proof/audits/`) 검토 도중 확인한, 프로젝트 규모와
개인 검증 능력 사이 격차 기록. 코드 품질 문제가 아니라 운영 원칙 문제라
별도 문서로 분리.

## 배경

세션 하나 분량의 작업만으로도 다음이 확인됨:

- 오케스트레이터가 실행하지 않은 `git reset`으로 로컬이 원격보다 뒤처진
  상태 발생 2회(병렬 세션 존재 추정)
- 로컬 SQLite 단일 유저 구조에서 Supabase(Postgres) + OAuth 멀티유저
  구조로의 아키텍처 전면 전환이, 검토 시작 전 이미 다른 세션에서 완료된
  상태로 발견됨
- 서버 코드 주석에 "독립 메모 기능 제거" 기록 존재 — 애초 정해둔 핵심
  기능 4가지(논문 목록/검색, 메모, 컬렉션, 웹페이지 추가) 중 하나가 별도
  확인 절차 없이 빠짐

변경 각각은 발생 시점 기준으로는 타당한 이유가 있었을 가능성이 높음.
쟁점은 "원래 정한 범위를 벗어나는 결정인지"를 매번 명시적으로 확인하고
넘어갔는지 여부.

## 범위를 좁게 유지한다는 것의 뜻

새 기능을 만들지 않는다는 뜻이 아님. **"이 변경이 원래 정한 경계를 넘는
결정인지 먼저 판단하고, 넘는 경우 진행 전에 확인받는 습관**을 뜻함.

작동한 예: `/guide` 페이지를 TabBar 새 탭으로 넣을지 물어본 뒤, CLAUDE.md에
이미 적힌 "웹 UI는 정해진 탭 이상으로 넓히지 않는다" 원칙과 충돌한다는 걸
확인하고 탭 대신 별도 URL 엔드포인트로 처리(관련 기록:
[design-references.md](design-references.md)).

작동하지 않은 예: 멀티유저 전환처럼 프로젝트 정체성을 바꾸는 결정이,
CLAUDE.md의 "1인용 도구" 전제와 충돌하는지 확인하는 절차 없이 이미
완료된 상태로 발견됨.

## 확인이 필요한 신호

아래에 해당하면 진행 전에 한 번 멈추고 확인 절차를 거칠 것.

- 아키텍처 자체를 바꾸는 변경(저장소 교체, 인증 방식 교체, 단일유저에서
  멀티유저로 전환 등)
- CLAUDE.md에 이미 명시된 범위·전제와 충돌하는 변경
- 기존에 있던 기능을 제거하거나 대체하는 변경
- 웹 UI 화면·탭 구성을 늘리는 변경

## 자동 검증의 한계

RepoProof 같은 외부 감사는 코드 결함을 찾는 데는 유효했음(이번 검토에서
확인된 버그 4건 전부 실제 결함으로 확인, 오탐 없음). 다만 정적 분석
단발 실행이라 다음은 보완하지 못함.

- 프로젝트 정체성·범위가 원래 계획과 맞는지 판단(코드 결함이 아니라
  운영·설계 판단의 영역)
- 시점 하나만 스냅샷으로 봄 — 이후 변경분은 재검증 전까지 미반영
- 실행 검증(runtime verification) 미실시(정적 분석만 수행)

결론: 자동 검증은 "사람이 코드를 다 못 읽는" 문제를 완화하는 보조 수단이지
대체 수단이 아님. 범위를 판단하고 확인받는 역할은 여전히 사람 몫으로 남음.
